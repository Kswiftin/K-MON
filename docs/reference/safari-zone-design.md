# 사파리존 — 4세대 그레이트 마쉬식 스테이지 포획 + 2D 걷기 화면

## 왜 전투 엔진이 없는가 — `WaveBattle` 을 재사용하지 않은 이유

그레이트 마쉬는 HP·기술·스피드가 없다. 매 조우에서 고를 수 있는 건 미끼/진흙/볼/도망 넷뿐이고,
포획률·도망률을 ±단계로 조정하다가 볼을 던져 승부를 보는 것이 전부다. 웨이브 런(`WaveBattle`)의
2대2 전투 엔진을 끌어올 이유가 없다 — 조우 하나의 상태는 `speciesID` + 포획단계·도망단계·턴
정수 셋이면 충분하다(`SafariEncounter`). 이 단순함이 사파리존을 웨이브 런보다 훨씬 작은 기능으로
만드는 지렛대다.

## 왜 2D 걷기 화면인가 — 접힌 던전 걷기 설계(spec 1)를 되살린 이유와 남은 비용

본가 사파리존은 벌판을 걸어 다니다 걸음마다 조우가 뜨는 방식이다. K-MON에는 이미 "오늘의 던전"을
출구 목록 클릭에서 방향키 걷기로 바꾸려던 설계(`room-walk-dungeon-design.md`, spec 1)가 있었지만,
실제 구현 전에 지금의 웨이브 런(버튼 선택식)으로 방향을 틀며 접혔다.

그런데 그 설계가 만들려던 **트레이너 걷기 스프라이트 엔진은 이미 완성돼 있었다** —
`TrainerSprite`/`TrainerPixelArt`/`Facing`이 4방향×3프레임을 이미 합성·캐시하고 있고, 착장
미리보기(`OutfitView`)가 이미 그 프레임을 걷기 애니메이션으로 재생한다. 당시 접힌 것은 격자
이동·문·방 전환(`DungeonWalker`/`RoomCanvas`/`KeyCapture`) 쪽이지 스프라이트 자산이 아니었다.

사파리존은 방-대-방 탐색이 없는 "한 벌판을 걷다가 걸음마다 조우가 뜨는" 더 얇은 루프라, 접힌
설계에서 문·방 그래프(`DungeonRoomLayout`)를 빼고 격자 이동 상태기계·키 캡처·게임루프만 새로
지으면 됐다.

**남은 비용(설계 당시 알린 것)**: `Canvas` 게임루프를 이 저장소에서 처음 짓는다는 것, `NSEvent`
로컬 모니터의 신뢰성, 벌판 배경이 정교한 타일 아트 없이 단색이라는 것. 첫 배포에서 실제로 걸린
결함 둘은 전부 이 신선함에서 왔다 — 아래 "알려진 거친 곳"과 `defect-log.md` 참고
(`nonisolated deinit`이 `Any?`를 못 읽는 문제, `NSView`(`@MainActor`)를 상속한 타입의 순수 함수가
자동으로 MainActor 격리를 상속해 테스트에서 호출 안 되던 문제 — 둘 다 Swift 6 엄격한 동시성
모드에서만 드러나 로컬 환경(Xcode 없음)에서는 못 잡고 CI가 잡았다).

## 판의 뼈대

방문(`SafariVisit`) → 존 선택 → 걷기(`SafariWalker`) → 조우(`SafariEncounter`) 반복 → 걸음
소진 또는 포획 상한 도달로 방문 자동 종료. 화면(`SafariZoneView`)은 이 흐름을 세 국면으로
갈아 끼운다: **존 선택**(`safariVisit == nil`, 스크롤 가능) → **걷기/조우**(방문 진행 중, 고정
레이아웃) → **방문 요약**(`hasEnded == true`).

## 포획률·도망률 단계 공식 — 명중률/회피율 공식을 가져온 이유

공식 자료에 없던 "단계별 배율표"를 임의로 짓지 않고, 본가가 3세대부터 명중률/회피율 랭크에 쓰는
공식을 그대로 가져왔다(`SafariZone.stageMultiplier`). 상승은 `(3+n)/3`, 하강은 `3/(3-n)`.
범위는 `stageRange = -3...3` — 본가 랭크(±6)의 절반이다, 사파리존 조우가 몇 턴 안에 끝나야
하므로 상한을 낮게 잡았다.

```
-3: 0.5×  -2: 0.6×  -1: 0.75×  0: 1×  +1: 1.33×  +2: 1.67×  +3: 2×
```

## 기저값 — `Rarity` 기반 고정 %를 재사용한 이유(`RaidBoss.catchPercent`)

기저 포획률은 `RaidBoss.catchPercent(for:)`를 그대로 재사용한다(legendary 5%, rare 15%,
uncommon/common 25%). 종별 실제 `capture_rate`를 쓰지 않는 이유는 `wave-run-design.md`의 포획
절이 이미 정리한 것과 같다 — 희귀도 축을 하나 더 두면 같은 일을 두 번 하는 셈이고, 종마다
`/pokemon-species` 왕복이 붙는다.

도망률은 **등급 없이 균일** 기저값(`baseFleePercent = 20`)을 쓴다. 등급을 또 개입시키면 "귀한
종일수록 도망도 잘 간다"는 이중 페널티가 생겨 희귀 포획이 사실상 불가능해진다.

둘 다 단계 배율 적용 후 **5~95% 클램프**(`RogueRun.catchChance`와 같은 관례) — 절대 안 잡히는/
무조건 잡히는 턴을 만들지 않는다.

## 턴 순서 — 미끼/진흙/볼/도망과 부작용 90%

| 행동 | 효과 | 부작용(90%) |
|---|---|---|
| 미끼(bait) | catchStage +1 | fleeStage +1 |
| 진흙(mud) | fleeStage −1 | catchStage −1 |
| 볼(ball) | 볼 1개 소모, 포획률 굴림 → 성공 시 조우 종료 | 실패해도 단계는 안 바뀜 |
| 도망(run) | 조우 즉시 종료, 볼 소모 없음 | — |

`SafariEncounter.act(_:rng:)`가 이 네 액션의 **유일한 진입점**이다 — 각각 별도 public
mutating func으로 안 쪼갠다. 쪼개면 나중에 새 게이트를 넣을 때 넷 중 하나를 빠뜨리기 쉽다
(`defect-log.md`가 경고하는 "새 게이트를 입력 경로 중 하나가 빠뜨리는" 결함 부류). 이미 끝난
조우(`outcome != nil`)에 다시 액션을 보내도 상태가 안 바뀌고 마지막 결과만 돌아온다 — 결과
배너가 떠 있는 동안 버튼이 다시 눌려도 안전하다.

결과는 `.caught`/`.fled`/`.ranAway`/`.timedOut`/`.continuing`을 **분리된 case**로 둔다
(`defect-log.md`가 경고하는 "쓰러짐과 이탈을 같은 값으로 뭉갠" 결함 부류를 피하기 위해).

조우당 턴 상한은 **20**(`maxTurnsPerEncounter`) — 단계가 ±3에서 포화되면 더 던져도 득이
없으므로 충분히 여유롭고, 무한 루프 가능성을 원천 차단한다. 상한 도달 시 `.timedOut`.

## 걷기 엔진 — `DungeonWalker` 설계에서 문·방 그래프만 뺀 이유

`SafariWalker`는 접힌 설계의 격자 이동 상태기계를 그대로 옮기되 문·방 전환만 뺐다. 벌판은
**단일 열린 구역**(`SafariFieldBounds.standard`, 14×9칸, 칸 24pt — 접힌 설계와 같은 치수, 팝오버
`contentWidth` 안에 들어가는 값이 이미 검증돼 있다)이라 바깥 테두리가 전부 벽이다.

- 칸 하나를 건너는 데 0.18초(`secondsPerCell`, 접힌 설계와 같은 값), `dt`는 0.1초로 클램프
  (`maxDeltaTime`) — 팝오버가 숨었다 돌아올 때 한 틱에 순간이동하지 않도록.
- 정지 상태에서 방향키가 눌려 있으면 그 방향 한 칸을 목표로 잡는다. 벽이면 방향만 바꾸고 제자리.
- `tick(dt:heldKeys:bounds:)`은 칸에 **새로 도착한 순간에만** `true`를 돌려준다 — 호출부
  (`SafariVisit.advance`)가 걸음 소모·인카운터 굴림을 정확히 한 번 실행해야 한다는 신호다.
- 조우 중(`currentEncounter != nil`)에는 `SafariVisit.advance`가 아예 `walker.tick`을 안 불러
  이동 입력을 무시한다.

장애물 없음(v1) — 접힌 설계도 spec 1에서 장애물을 뺐던 것과 같은 이유(범위 최소화). 마우스
폴백도 v1 범위 밖이다.

**입력**은 `SafariKeyCapture`(`NSEvent` 로컬 모니터)가 방향키·WASD를 소비한다. SwiftUI의
`dismantleNSView`가 화면이 사라질 때(탭 전환·오버레이 닫힘) 모니터를 확실히 해제한다.

**게임루프**는 `Canvas` + `TimelineView(.animation(minimumInterval: 1/60, paused:))`다.
`TimelineView`는 렌더링만 하고, 실제 물리 업데이트(`SafariVisit.advance`)는
`.onChange(of: context.date)`에서 건다 — 뷰 업데이트 도중 상태를 바꾸지 않기 위해서다. 화면이
안 보이면(`onDisappear`) paused로 돌려 상시 애니메이션을 막는다("상시 애니메이션" 부류,
`defect-log.md`). 트레이너 스프라이트는 착용이 바뀔 때만 다시 굽는다(`TrainerAvatarView`와
같은 이유) — 매 프레임 합성 금지.

## 걸음 500·조우당 턴 20 — 두 예산이 다른 축인 이유

2D 이동이 생겨 원본의 "500걸음"(`stepsPerVisit`)을 걸음 카운터로 그대로 옮겼다 — 버튼식이었다면
억지였을 개념이 실제 이동이 생기면서 자연스러워졌다. 방문 자동 종료 조건은 **둘**: 걸음이
0이 되거나(조우 중이 아닐 때), 포획 여유(방문당·하루)가 바닥나거나. 실전에서는 포획 상한이
걸음보다 훨씬 먼저 닿을 것이므로 걸음 소진은 "운이 나빠 계속 놓친 경우"에나 실제로 발동하는
안전판에 가깝다. 조우 턴 상한(20)은 걸음과 별개로 유지된다 — 조우 중엔 걸음이 안 깎인다(조우는
"그 자리에 멈춰서 푸는" 미니게임이라 이동 예산과 다른 축이다).

## 입장료를 두지 않은 이유 — 일일 방문 상한과의 대체 관계

레이드·웨이브 런 둘 다 입장료가 없다는 선례를 따른다. 원본의 500(게임화폐) 입장료를 옮기는 안을
검토했지만 기각했다 — 실질적 역할(무한 재입장 방지)은 하루 방문 상한(`dailyVisitCap = 3`)이
화폐 없이도 같은 일을 한다.

## 참여 상한과 포획 상한을 분리한 이유

**최초 설계의 문제**: 볼 30개(본가 그대로) + 하루 포획 상한 없음이면 한 방문에 이론상 최대
30마리, 하루 3방문이면 최대 90마리를 영구 도감/보관함에 등록할 수 있었다. 웨이브 런은 "판이
끝나면 잡은 포켓몬은 사라진다"(휘발성이라 애초에 경제와 안 부딪힘), 레이드는 하루 최대 6마리
(티어 3 × 반나절 2, 승리까지 필요)로 묶여 있어, 전투 없이 걷기만 해도 영구 등록되는 채널에
상한이 없으면 레이드의 15배를 뽑아낼 수 있는 구멍이었다.

**처방**: 레이드의 하루 6마리를 목표치로 잡고 **"방문당 2마리(`catchesPerVisitCap`) × 하루
3방문(`dailyVisitCap`) = 6마리(`dailyCatchCap`)"**로 확정했다 — 두 상한이 정확히 맞물리는
숫자다. 볼은 30개에서 **10개**(`ballsPerVisit`)로 줄였다 — 방문당 잡을 수 있는 건 최대 2마리뿐
이라 30개는커녕 15개도 대부분 못 쓰고 버려진다.

원장은 **볼·걸음(참여 자원)과 포획 상한(보상 자원)을 분리된 두 카운터**로 관리한다 —
`SafariVisit.catchesThisVisit`(방문 로컬, 방문이 끝나면 사라짐)와
`CompanionStore.safariZoneCatchesRemainingToday`(세이브 원장, `state.safariZoneCatchDate`/
`safariZoneCatchesToday`). `raidRewardDate` vs `raidCatchDate`를 가르는 것과 같은 이유다 —
하나로 합치면 "얼마나 노는지"와 "얼마나 가져가는지"가 뒤섞여 한쪽이 다른 쪽의 상한을 태운다.

## 포획 여유가 바닥나면 방문을 자동 종료하는 이유

새 조우가 뜨려면 방문당·하루 두 상한을 **동시에** 만족해야 한다
(`min(catchesPerVisitCap - catchesThisVisit, catchesRemainingToday) > 0`). 둘 중 하나라도
0이면 `SafariVisit.advance`가 새 조우를 굴리지 않고 **그 자리에서 방문을 끝낸다**
(`hasEnded = true`) — 볼·걸음이 남아 있어도다.

새 조우를 안 굴리기만 하고 계속 걷게 두는 것은 이 부류의 처방이 아니다 — 포획 여유가 없으면
더 걸을 이유가 없다. 그대로 두면 플레이어가 이유 없이 빈 벌판을 계속 헤매게 된다. 판정은 조우가
없는 시점에만 확인한다(조우 중이면 그 조우가 끝난 뒤 확인) — 조우 도중에 방문이 사라지면 결과
배너를 보여줄 화면이 없어진다.

이중 방어: `CompanionStore.catchInSafariZone`도 커밋 직전에 `safariZoneCatchesRemainingToday
> 0`을 다시 확인한다. 소스 차단(조우 자체를 안 굴림)과 커밋 차단(만에 하나 조우가 이미 진행
중이던 상태에서 자정을 넘기는 경계 상황)을 둘 다 두는 이유는, 한쪽만 있으면 그 경계 케이스가
새는 부류(`defect-log.md`의 "게이트 누락")가 재발할 수 있어서다.

## 볼은 세션 임시 자원이다 — `ItemKind`에 넣지 않은 이유

기존 아이템(`ItemKind`)은 전부 세이브에 영속 저장되는 인벤토리 항목이다. 사파리 볼처럼 "이번
방문에서만 쓰는 소모품"은 그 패턴이 아니다 — 레이드의 `pendingRanked`(에스크로) 같은 **세션
한정 임시 상태**에 더 가깝다. 그래서 `SafariVisit.balls`는 방문이 끝나면(`store.safariVisit =
nil`) 함께 사라지는 방문 로컬 필드다.

## 존 설계 — 큐레이션 풀 방식과 `speciesTypeIndex`를 안 쓴 이유

`RaidBoss`처럼 **정적 큐레이션 배열**(`SafariZone.gradePools(for:)`)을 쓴다. 런타임
`speciesTypeIndex()` 필터를 기각한 이유는 셋이다 — 결정론 테스트 가능성, 오프라인 조우 복원
(`PokeAPIClient` 네트워크 의존 없이 조우를 뽑을 수 있어야 진행 중인 방문을 복원할 수 있다),
콘텐츠·로직 분리(종 목록은 코드 로직과 다른 성격의 작업이라 분리하는 편이 리뷰하기 쉽다).

**존 3개로 시작**(`grassland`/`wetland`/`cave`) — 선택의 여지가 없다는 느낌과 초기 콘텐츠 과잉
사이의 중간. 각 존의 종 목록은 **placeholder**다(존당 4종, 존 테마에 맞춘 자리 표시자) — 실제
라인업은 별도로 확정한다.

## 등급 가중치(일반 75%·고급 18%·희귀 7%, 전설 없음) — 알의 두 원칙을 존 규모로 옮긴 이유

**최초 설계의 공백**: `chooseEncounter`가 존 풀 전체에서 균등 추첨이었다. 존 풀은 레이드 풀처럼
작은 목록(존당 4~10여 종)이라, 그 안에 전설을 하나만 넣어도 균등 추첨에선 1/(풀 크기) ≈ 6~7%로
뜬다 — 반면 알(`FreshEgg`)은 보증 없이 사면 전체 획득 가능 종(~1,000종)에서 뽑혀 등급 비율이
실제 `capture_rate` 분포에서 자연히 나오고(고급 약 7.16%, 희귀 약 6.98%), **전설 전용 알은 아예
안 판다**("최고 등급을 확정 상품으로 만들지 않는다"). 균등 추첨을 그대로 두면 사파리존이 알보다
훨씬 쉽게 전설을 흘리는 채널이 되어 알·레이드의 자리를 갉아먹는다.

**처방**: 알의 두 원칙을 그대로 가져왔다.
- 존 풀에는 전설을 넣지 않는다 — 전설은 계속 레이드(노리고 가는 전설)와 알(무작위 서프라이즈)의
  몫으로 남긴다.
- 일반/고급/희귀 사이는 균등이 아니라 **가중 추첨**이다. 알의 실측 비율에 맞춰 **일반 75%·고급
  18%·희귀 7%**로 잡았다(`SafariZone.chooseEncounter`) — 알처럼 전체 ~1,000종에서 나온 자연값이
  아니라 존 규모(10여 종)에 맞게 재현한 것이라, 정확한 알고리즘을 복제하진 않는다.

## 포획은 즉시 영구 반영된다 — `RogueRun`과 다른 점(휘발 vs 영속)

잡은 개체는 `CompanionStore.catchInSafariZone`이 즉시 영구 도감/보관함에 반영한다(레이드와
동일). 웨이브 런의 "판이 끝나면 잡은 포켓몬은 사라진다"와 정반대다 — 사파리존의 존재 이유가
"포켓몬을 잡아 도감을 채우는 것"이므로 휘발성이면 기능 목적 자체가 사라진다.

`catchInSafariZone`은 `catchRaidBoss`와 개체 생성·배치·기억·알림 경로(`commitCaughtMon`)를
공유하고, 원장 가드만 다르다(레이드는 티어별 하루 1회, 사파리존은 방문당·하루 이중 상한).
`catchRaidBoss`는 레이드 풀이 전부 최종 진화체라는 전제로 `pathIDs: [speciesID], stageIndex: 0`
을 단순 대입한다 — 사파리존 존 풀도 이 전제를 지켜야 한다(비-최종진화체를 넣으면 이 대입이
더 이상 맞는 뜻인지 다시 확인해야 한다).

## 진행 중인 방문은 디스크에 남는다 — 곁파일 저장 방식

`SafariVisit`은 `RogueRun`과 마찬가지로 세이브 본체가 아니라 **옆 파일**(`safari-zone.json`)에
산다 — 방문은 재화도 도감도 직접 주지 않으므로(포획 커밋은 `catchInSafariZone`이 별도로 하고
그 결과만 세이브 본체에 남는다) 무결성 서명과 세이브 이전 경로에 닿지 않는다.

`SafariVisit` 자체는 `Codable`을 준수하지 않는다 — `SplitMix64`가 `Codable`이 아니라서다(씨앗과
"소비된 뒤의 상태"를 분리해서 저장해야 다음 굴림이 재시작 후에도 이어진다). `SafariZoneSave`가
그 변환을 전담하는 저장 브리지다(`RogueRunSave`와 같은 모양) — `rngState`(소비된 뒤 값)만 별도
필드로 싣고, `seed`(고정값)는 그대로 싣는다. 모르는 형식 판(`version`)은 방문을 버린다 —
진행 중인 방문은 소모품이고, 반쯤 읽어 되살린 방문이 처음부터 다시 시작하는 것보다 나쁘다.

방문·포획 두 원장(`safariZoneVisitDate`/`Today`, `safariZoneCatchDate`/`Today`)은 세이브 본체
필드다 — 무결성 서명(`szv`/`szc` 세그먼트, `integrityVersion`은 안 올림)·기기 병합(같은 날이면
많이 쓴 쪽, 다른 날이면 최근 쪽 — `mergedGymDefenseLedger`와 같은 규칙)에 포함되지만
`sanitized()`에서 0~하루 상한으로 클램프될 뿐 끌어올려지지 않는다.

## 알려진 거친 곳

- **존 3개·placeholder 종수**: 실제 라인업 큐레이션은 후속 결정.
- **장애물 없음·마우스 폴백 없음**: v1 범위 밖 — 필요하면 후속 PR.
- **벌판 배경은 단색**(존별 다른 `Color.opacity`): `MemoryHomePixelArtSprites.swift`와 같은
  방식의 정교한 픽셀 타일 아트는 짓지 않았다 — 존 큐레이션과 같은 수준(placeholder)으로 최소화.
- **Swift 6 엄격한 동시성**: 이 환경(Xcode 없음)은 Swift 5 언어 모드로만 로컬 타입체크가
  가능해, `nonisolated deinit`의 `Sendable` 위반과 `NSView`(`@MainActor`) 상속 타입의 순수
  함수가 격리를 상속하는 문제 둘 다 로컬에서 못 잡고 CI에서 드러났다. 앞으로 `NSViewRepresentable`
  류를 더할 때 미리 염두에 둘 부류다.
- **TimelineView가 idle에서 실제로 멈추는지, 걷기·조우 전환이 매끄러운지**: 유닛 테스트로 확인할
  수 없다 — 앱에서 육안 확인이 필요하다.
