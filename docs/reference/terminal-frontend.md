# 터미널 프런트엔드

메뉴바 앱과 **같은 실행 파일**이 터미널에서도 돈다. `pokedoro status` 처럼 한 번 찍고 끝나는 명령이
본체이고, `pokedoro watch` 만 전체 화면으로 오래 산다.

**터미널은 세이브를 읽기만 한다.** 모험 시작·정산·취소는 앱에만 있다. 이유는 아래 "왜 읽기 전용인가".

## 왜 실행 파일을 나누지 않았나

SwiftPM 은 두 타깃이 같은 소스 디렉터리를 나눠 쓰는 것을 허용하지 않는다. 게임 로직(`Core`, 약
25,000줄)을 별도 라이브러리 타깃으로 떼면 그 안의 타입에 전부 `public` 을 붙여야 한다. 얻는 것보다
비용이 크므로 **한 실행 파일에 두 진입점**을 뒀다(`PokedoroEntryPoint`).

어느 쪽으로 갈지는 `PokedoroCommandParser.isTerminalInvocation` 이 정한다. 판정 기준은 **파싱 성공
여부가 아니라 인자의 생김새**다.

- 셸에서 친 인자는 `-` 로 시작하지 않는다 → 터미널.
- macOS 가 앱 번들에 붙이는 인자(`-NSDocumentRevisionsDebugMode`, `-psn_…`)는 항상 `-` 로 시작한다 → 앱.
- 예외로 `--tui` · `--cli` · `--help` · `-h` 는 터미널로 본다.

파싱 성공 여부로 가르면 **오타가 메뉴바 앱을 띄운다**. 사용자는 자기가 뭘 잘못 쳤는지 알 수 없고,
앱이 하나 더 뜬 것도 눈치채기 어렵다.

## 왜 읽기 전용인가

메뉴바 앱과 터미널은 같은 `companion-state.json` 을 본다(`PTB_STATE_DIR` 로 격리 가능). 두 프로세스
사이에 잠금이 없어 **쓰기를 양쪽에 두면 두 가지가 깨진다.**

1. **세이브를 여는 것 자체가 진행을 바꾼다.** `CompanionStore` 의 기동 경로는 "앱이 죽은 사이 밀린
   일" 을 처리한다 — 정산 없이 끝난 랭크전을 패배로 마감하고, 끝난 모험을 정산하고, 앨범을
   정리한다. 그 전제는 이 파일을 여는 프로세스가 하나일 때만 참이다. 앱이 랭크전을 하는 중에
   터미널이 `pokedoro status` 를 열면 **그 배틀이 패배로 정산된다.**
2. **나중 쓰기가 앞 쓰기를 통째로 덮는다.** 세이브 쓰기는 `.atomic` 이라 파일이 손상되지는 않지만,
   앱이 그 사이 올린 진행은 사라진다.

그래서 터미널은 `CompanionStore(isReadOnly: true)` 로 연다. 이 생성 경로는 ⓐ 디스크를 읽는 데서
멈추고(위 정리·정산을 건너뛴다) ⓑ `save()`·`persistRogueRun()` 을 no-op 으로 만든다. ⓑ 가 따로
필요한 이유는, 화면을 그리다 부수효과가 있는 계산을 밟아도 세이브가 나가면 안 되기 때문이다.
검증은 `ReadOnlyStoreTests` 가 **파일 내용 그대로**로 한다.

쓰기를 터미널에 다시 들이려면 잠금이 먼저다. 그때도 "잠금을 못 잡은 쪽이 조용히 저장을 멈추는"
상태를 만들지 않아야 한다 — 그 실패는 사용자에게 보이지 않아 원래 문제보다 나쁘다.

`watch` 는 오래 사는 유일한 경로라 화면 값이 낡는다. 5초마다 디스크를 다시 읽어 앱이 올린 진행을
끌어온다. 다시 읽는 저장소도 읽기 전용이라 이 화면이 도는 동안 세이브에 나가는 쓰기는 없다.

## 터미널 칸 계산

터미널은 픽셀이 아니라 칸으로 배치한다. 한글·CJK·이모지는 한 글자가 두 칸이므로 `String.count` 로
자르거나 채우면 **한국어 이름에서만** 정렬이 깨진다. 영어 이름으로 확인하면 못 보는 부류다.

- 폭 계산은 `TUIText.displayWidth` 한 곳에만 둔다.
- 넓은 글자 판정은 범위 표 + 유니코드 `Emoji_Presentation` 속성이다. 범위 표만 쓰면 ✨(U+2728)처럼
  CJK 블록 밖의 두 칸짜리 기호를 놓치고, 범위를 손으로 넓히면 같은 블록의 한 칸짜리 기호(✓)까지
  두 칸으로 세어 반대로 어긋난다.
- 경계에 두 칸짜리 글자가 걸리면 **버린다**. 반쪽을 내보내면 그 줄부터 커서 열이 어긋나고, 전체
  다시 그리기로는 복구되지 않는다.

## 키 입력 해석

raw mode 의 stdin 은 바이트열이다. `TUIKeyDecoder` 가 그것을 키로 바꾸며, 세 가지가 깨지기 쉽다.

- **ESC 단독.** 한 바이트만으로는 화살표 시퀀스(`ESC [ A`)의 첫 바이트와 구분되지 않는다.
  `decode` 는 판단을 미루고, 입력이 잠시 멎으면 `flush` 가 ESC 로 확정한다. 이 확정이 없으면
  ESC 키가 영영 죽는다.
- **모르는 시퀀스**(Home·PageUp)는 `.unknown` 이라는 자기 자리로 돌아온다. 문자로 접으면 진짜
  입력과 구분되지 않는다.
- **잘려 온 UTF-8.** 앞이 잘린 이어지는 바이트(0x80–0xBF)를 Latin-1 문자로 읽으면 한글 한 글자가
  알파벳 여러 개로 흩어져 그중 하나가 화면 전환 키로 먹힌다. 그런 바이트는 `.unknown` 이다.

## 화면에 쓰는 값은 세이브에서만 꺼낸다

`CompanionStore` 의 일부 표시값은 PokéAPI 에서 **비동기로 받아 온** 진화 라인이 있어야 채워진다
(`displayName`·`speciesName`·`currentTypes`·`currentStats`·`displayedMoves`). 메뉴바 앱은 오래 살아
곧 채워지지만, 짧게 살다 죽는 명령은 그 전에 끝나므로 **언제나 자리표시자**(`"Token Egg"`)만 본다.

터미널은 세이브에 저장된 값을 읽는 경로만 쓴다 — 이름은 `chatRosterEntries`, 도감은 `dexSpecies`.
새 값을 화면에 올릴 때 같은 함정을 다시 밟지 않으려면 "이 값이 네트워크 없이 나오는가" 를 먼저 본다.

## 명령

```
pokedoro status [--oneline]   파트너·모험·잔액 (--oneline 은 상태줄용 한 줄)
pokedoro party                보유 포켓몬
pokedoro dex                  도감
pokedoro watch                전체 화면 실시간 보기
```

종료 코드는 `0` 성공, `1` 인자 오류다. 앱에만 있는 명령(`start`·`claim`·`cancel`)은 이름을 알아보고
**어디서 해야 하는지 답한다** — "알 수 없는 명령" 으로 뭉개면 사용자는 오타를 의심하며 같은 명령을
다시 친다.

앱 번들 안의 실행 파일이 그대로 이 명령이다. 셸에서 짧게 부르려면 링크를 하나 건다.

```sh
ln -s "/Applications/Pokédoro.app/Contents/MacOS/PokeTokenBar" /usr/local/bin/pokedoro
```

tmux 상태줄에 붙이는 예.

```
set -g status-right '#(pokedoro status --oneline)'
```

## 테스트

터미널 프런트엔드의 순수 부분(폭 계산·렌더·키 배정·명령 파싱)은 전부 부수효과가 없어 단위 테스트가
닿는다 — `TUITextTests`·`TUIRenderTests`·`TUIInputTests`·`PokedoroCommandTests`. 세이브를 여는
쪽은 `ReadOnlyStoreTests` 가 본다. 이들은 **swift-testing** 으로 써서 `Tests/PokeTokenBarLocalTests`
에 두므로 Xcode 없이 `./scripts/test-local.sh` 로 실제로 돌아간다(`XCTest.framework` 만 Xcode
전용이다).

터미널 제어(`TUITerminal`)와 실행 루프(`TUIWatch`)는 테스트 대상이 아니다. 그래서 그 둘에는
**판단을 두지 않는다** — 무엇을 그릴지·어떤 키가 무엇인지는 전부 순수 쪽에 있다.
